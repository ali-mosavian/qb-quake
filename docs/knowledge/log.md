- 2026-08-24 — new `surface-cache-and-standalone-testing.md`: a DC costs sizeof(DC)+yRes*4 bytes of CONVENTIONAL memory for its scanline table, and the first surface cache gave one DC per cached surface — 228 on dm3ish, against a pool sized for up to 1,200, which wedged DGROUP ("String space corrupt" after rendering fine for a while). Fixed by adding `uglNewView`/`uglSetView`/`uglDelView` to uGL (`mgl/src/ugl/uglview.asm`): numpy-style views, a DC's shape+clipping over a parent's pixels, no memory of its own. Every texture filler already does `xor si,si` before rdAccess, so aiming a view for drawing is one dword write; only the builder path (uglRowRead/uglPSet, which index per scanline) needs the whole address table. Kept as `uglDelView` rather than teaching `uglDel` to recognize a view, specifically to avoid a DC struct change — that moves DC_addrTB and forces reassembling all 31 modules that reference it, against a uglv.lib already known stale. Result: 228 DCs → 21, pixel-identical render, verified. Applying the same trick to the 160 texture DCs is currently hung on a bug standalone testing could NOT reproduce (same library, same uglNewBMPEx+row-copy pattern, runs clean and byte-verifies) — so it's specific to qrender's own context, not the library or the row-copy logic, still open. Getting a trustworthy standalone repro cost five separate false negatives, all now documented: CRLF (BC silently mis-tokenizes LST-only line breaks instead of hard-erroring), $INCLUDE paths being relative to compiler CWD not source location, BC needing an explicit `, file.obj` destination or it silently produces a wrong stub, `/E` being a multi-module-project flag that produces a linked-but-inert EXE when misapplied to a standalone test, and the full library needing `/SEG:800` to link at all once uglview.asm pushed module count over LINK.EXE's default segment limit.
- 2026-08-24 — new `map-data-compression.md`: the full compression pass over the level data, ~89 KB reclaimed on dm3ish (level lumps 313,873→265,699 B, scratch 16,384→5,258 B, lightmaps 71,307→40,677 B). Methods: dead-field drops (`face.lightmap`, `texinfo.flags` — the latter compiler-only, baked into per-face `lightofs`/`styles`), long→integer narrowing range-verified against all 10 available maps, the unsigned-in-int16 two's-complement wrap for `face.ledgeid`, Q13.3 fixed-point vertices (Q12.4 fit dm3ish but overflowed 6 of 9 shareware maps — never size a format from one map), and per-face 4-bit lightmaps (base+range, 16 linear levels; global palette banded at step ~15, per-plane median step is ~2.3; wide planes get a bilerp-mass-matrix ICM fit, threshold 120 derived from one-colormap-row error). Also the clip.bld size-mismatch incident: a stale packer BLOADed 8-byte records into a 6-byte-record buffer — hard fault on frame 1 that bypassed `ON ERROR GOTO` and looked like a clean exit; the TYPE, the packer, and the tmp-type twin must move together.
- 2026-08-24 — new `dos-mcb-memory-diagnosis.md` and `qrender-memory-map.md`: a 16 KB `memAlloc`/`REDIM` for the surface builder's colormap table hung the program with no error, while `memAvail&` reported ~260,000 bytes free. Root cause required abandoning BASIC's own memory introspection (`memAvail&`/`SETMEM`/`FRE`, which measure BASIC's far-heap *size*, not DOS's actual free memory) and walking DOS's MCB chain live in the dosbox-x debugger instead: DOS had exactly 9,312 bytes free system-wide, so the 16 KB request was arithmetically impossible to satisfy honestly — mgl's `bas_malloc` retry path (shrink BASIC's heap via `B$SETM`, retry `int 21h/48h`) handed back a block that didn't correspond to real headroom on an arena this fragmented, and a bare `REDIM`'s zero-init then corrupted whatever was actually there. Documented the walking method (4096-byte-per-read cap, `align:16` required or false positives are overwhelming, identify blocks by content not size since two disjoint origins — explicit `memAlloc()` calls carry mgl's own header, BASIC's automatic heap growth doesn't) and the full current memory map for dm3ish: DOS-side (9,312 B free total, `lm_base`/`lm_info`/font-atlas/texture-DC-structs identified by content, not guessed) and BASIC's-own-far-heap-side (249,005 B computed array-by-array vs. 248,672 B measured, 0.13% residual = allocator overhead). Fix identified: move `lm_base` (71,328 B) + `lm_info` (36,704 B) to XMS, reclaiming 108 KB; UMB is already linked and already fully consumed, not an available lever.
