- 2026-08-31 — two investigations, both concluding in measured negatives, both documented so they are not repeated. **Span rendering**: a complete Quake-style global edge list -> sorted span renderer was built (`src/r_span.c`), given entry points into uGL's own scanline filler (`uglSpanBegin`/`uglSpanTP` in `uglspan.asm`), made correct against the polygon path, and benchmarked: 56.75 vs 47.97 ms/frame, 18% slower, and nearer 13 ms slower like-for-like since the span arm forces `UGL_Z_OFF` and writes no depth while the polygon arm writes it per pixel. Bracketing the mapper's outer loop decomposed the frame into per-polygon setup 13.2 ms (55%), fill 8.3 (35%), and all per-scanline work 2.5 (10%) — so the largest item is invariant to the architecture, since the same 208 polygons are resolved either way, and the resolve costs ~23 ms to remove ~8 ms of avoidable fill. Overdraw is a property of the map and is small: 1.418x on dm3ish, 1.556x on e1m7 — and e1m7 comes out *worse* despite more overdraw, because its geometry is more, smaller polygons describing the same covered area with 20% more crossings. Four optimisation rounds cut the resolve 17.82 -> 8.15 ms first (16.16 fixed point and a near-unpacked AEL, killing an `F_FTOL@` *helper call* per crossing; a doubly-linked AEL with sentinels where merge, step, expire and repair share one walk; the polygon's emission index as an integer depth key, which also collapsed `toggle_active` to a single scan; and an emit rewrite that proved two of six clamps unnecessary by clamping vertices rather than the values derived from them). Two measurement corrections are worth more than the result: a per-crossing RDTSC bracket cost 1.25 ms of a 7.85 ms sweep, a third of what it reported, so anything finer than a per-frame phase must be measured by removing the work rather than timing it in place; and "608 ticks per scanline" was an artifact of deriving cost by subtracting `fill` from `mappers`, when bracketing the whole outer loop showed 55% of that never enters the scanline loop at all (real figure ~166). Host load turned out not to contaminate any of it — all four rounds were measured with a stray DOSBox running 10 hours at 6% CPU, and re-measuring on a quieter host reproduced three of four phases within 1%, with two runs agreeing to three decimal places, which validates the `cycles=75000` pinning rule empirically. Correctness took five bugs, three found by isolated tests that the renderer could not have surfaced (a return value clobbered by the z-mode restore, invisible because the renderer ignores it; `es:di` not addressing the destination at all, because `wrBegin` indexes the scanline table with `di` on entry and a table entry is segment-in-low-half not offset-in-low-half, which was corrupting the BASIC heap and presenting as a wedge in `B$ONERR` with no output; and u/v needing to be texels/z since `uglPolyTP` does that scaling above where these entry points hook in), one they structurally could not (the texture handles are ~8 shared views re-aimed per face with `uglSetView`, so deferring the draw to a sweep means every span draws through whatever cell the view was last pointed at), and one that only real geometry produces — `d_clip_z` hands over clipped polygons whose leading vertices are often nearly collinear on screen, so fitting the plane through vertices 0,1,2 failed the determinant test and *silently dropped whole faces*; picking the best-conditioned triple took grossly-wrong pixels from 1.9% to 0.0%. **Flat addressing**: separately, whether segment 0 plus a 32-bit offset reaches 1MB in real mode. DOSBox-X says yes (7,168 bytes across seven regions, zero mismatches); bochs says #GP in four independent configurations, including one verified to be genuine V86, and bochs matches the architecture. The address-size override widens the offset, not the segment's reach. V86 cannot be made to do it either — the limit is imposed by the mode and entering V86 reloads all six segment registers, destroying any oversized cached limits, which is the mechanism behind `flat_real_mode_demo`'s "Works with EMM386: No". Also established, against the starting assumption: a DPMI host does *not* put the CPU in V86 — neither `CWSDPMI -P` resident nor after a real DPMI client had switched to protected mode and exited (both `PE=0`); only HIMEM+EMM386 reported `PE=1`. CWSDPMI is a server that switches for its client and drops back; a persistent V86 monitor comes from a memory manager. Three vacuous versions of this test were caught before being reported: a target at linear 51,078 (under 64K, so success proved nothing), BIOS ROM reading 0 both ways and "passing" on 0 == 0, and two arms producing byte-identical output that an `SMSW` check revealed to be the same test run twice — two of the three DPMI arms would have been meaningless without it. The general lesson is that any low-level assumption verified only under DOSBox is unverified; a boot sector plus port `0xE9` under bochs is a 30-second check needing no DOS, no ROMs and no image building.
- 2026-08-24 — two findings, one reverted change. The lightmap "streaks" (dashed trim lines under `-lm`, present since the first working `-lm` build) are not a dark groove breaking up but *light* pixels appearing where none can exist: the unlit path draws through colormap row 0, the brightest row, so a lit pixel brighter than its unlit counterpart is impossible. Counting those gives 269 on dm3ish at spawn+35, and mapping them traces exactly the trim lines and floor speckle — a regression metric to score fixes against instead of squinting at crops. Cause: `sc_mipfloor` clamps `lm_mip` up so a surface fits the single 16K EMS page the filler maps, so a 224x224-extent face (256x256 padded = 65,536 bytes at mip 0) is forced to mip 1 (128x128 = exactly 16,384); a coarser mip box-averages a one-texel dark groove with the bright mortar beside it, landing above what row 0 can produce. Measured 26 of 374 faces building coarser, every one with `lm_floor = 1`, all of them the big wall and floor faces. Consequence of the one-page limit, not a coding bug — Quake's surface blocks are not capped at 16K. Eight hypotheses eliminated with evidence and recorded so they stay eliminated: lightmap precision (raw 8-bit, Quake's own, still dashes), `fit_plane` on/off/always, row truncation vs rounding, surface content, view aiming (fresh-view dump byte-identical across 37 pages), a constant half-texel phase (both directions worse — 484 and 479 vs 269), non-square textures in the square atlas (streaks are on 64x64 ones), and coarser mips as a fix (removes the dash by destroying the detail, and adds mip seams). Separately, the texture store from earlier today was REVERTED (a9ee111): unlit byte-identical, but `-lm` differs 87.9% at that camera with identical geometry and cache stats, and 67% of the cached surfaces' own pixels differ, so it corrupts at surface-build time for reasons still unknown — the packed stores, the offsets, the texels read back through the view, and every lightmap/colormap asset all verify correct. It landed because the unlit path was pixel-diffed against a baseline while `-lm` was only eyeballed at one camera, and the default yaw is an angle where both builds agree. Also: a surface dump that tiles into one 320x200 DC silently discards everything past ~12 surfaces (the frame builds ~440) and, unless reset per frame, smears every frame together — page it, reset it, and confirm a landmark texture is present before trusting that the camera has settled.
- 2026-08-24 — surface cache: found the hard ceiling on any single EMS `DC` while trying to grow it to 16 MB. `ems_New` packs a scanline's logical page into one byte of the addrTB entry, incremented with `adc dh, 0` and never checked for overflow, so page 256 wraps to 0 and silently aliases page 0 — a 16384-wide store maxes at 256 pages, 4 MB, no matter how much EMS is actually free. Recognized because it produced the exact same red/white streak signature as the `uglNewView` handle bug fixed earlier the same session, which is now worth treating as a general tell: that visual pattern means "reading the wrong EMS page," regardless of which of the two now-known causes. Bracketed with an isolated fresh-DC-per-size sweep (16 through 300 rows): byte-perfect through exactly 256, 233/257 rows wrong the instant 257 is requested, no partial zone — a single 300-row DC swept in place first gave a messier, misleading pattern from leftover test state, so isolate before trusting a boundary. Set `SC_PAGES = 256` (4 MB, was mistakenly 1024/16 MB), verified `sctest 1` and pixel-identical to the working 1.5 MB build. The texture store shares the same ceiling at 2048 wide (512 KB, ~91 textures for dm3ish's per-texture cost) — not hit yet, not guarded against at asset-build time.
- 2026-08-24 — `surface-cache-and-standalone-testing.md` rewritten around the root cause the texture-store work had been chasing for a session: `ul$fillView` built a view's EMS scanline table with `mov dh, al`, writing the logical page over the handle word's high byte. `ems_New` *accumulates* it (`adc dh, 0`), so the correct instruction is `add dh, al`; the old form is only harmless while EMS handles stay under 256, which is true for a program's first few allocations and false afterwards. A view over any later-allocated DC therefore addressed a different handle's pages — qrender's texture store read 227 where 45 was expected, and drew valid textures on the wrong surfaces rather than noise. The same bug was live in the surface cache the whole time and invisible there, because it writes surfaces through views and draws through views: identical wrong base on both sides, correct picture, "verified pixel-identical". Four standalone tests passed while it was live, each vacuous in a different way now recorded: none tested a view over a `uglNewBMPEx` parent (the actual pairing), all allocated their subject first (exactly where a handle-high-byte bug cannot show), one used a grayscale `(i,i,i)` palette where a nearest-colour remap IS the identity so it "proved" `BMPOPT.NO332` was honoured, and one wrote and read through the same view so it passed regardless of where the view pointed — the check that mattered was view-vs-direct. Those false negatives produced, in order, the wrong conclusions that the library rebuild was fine, that `uglview.asm` was fine, that `uglPutBMPEx` was broken on wide images, and that `uglNewBMPEx` was remapping the palette. Adding three throwaway EMS DCs before the subject reproduced it on the first try. Separately: most of a session was spent calling a headless run a hang when it was `qrender.exe` invoked without `-bench`, which runs interactively forever; and `-bench N` is not a deterministic comparison basis (it counts frames, so a different `dt` walks the camera elsewhere and ~97% of pixels differ) — `-ticks N` is. With the fix, the texture store landed: mkassets.py packs every texture and mip into one 2048-wide image at the offset a view is aimed at (2048 divides the 16K EMS page evenly and stays under uGL's 8192-byte scanline cap) plus a `texofs.bld` emitted rather than recomputed, `mod_load_textures` does one `uglNewBMPEx` per texel set, and dm3ish goes from 160 texture DCs and 160 asset files to one store plus four views and three files, ~12.3 KB of conventional scanline tables to ~0.9 KB (~24.6 KB to ~1.7 KB under `-lm`), rendering pixel-identical.
- 2026-08-24 — new `surface-cache-and-standalone-testing.md`: a DC costs sizeof(DC)+yRes*4 bytes of CONVENTIONAL memory for its scanline table, and the first surface cache gave one DC per cached surface — 228 on dm3ish, against a pool sized for up to 1,200, which wedged DGROUP ("String space corrupt" after rendering fine for a while). Fixed by adding `uglNewView`/`uglSetView`/`uglDelView` to uGL (`mgl/src/ugl/uglview.asm`): numpy-style views, a DC's shape+clipping over a parent's pixels, no memory of its own. Every texture filler already does `xor si,si` before rdAccess, so aiming a view for drawing is one dword write; only the builder path (uglRowRead/uglPSet, which index per scanline) needs the whole address table. Kept as `uglDelView` rather than teaching `uglDel` to recognize a view, specifically to avoid a DC struct change — that moves DC_addrTB and forces reassembling all 31 modules that reference it, against a uglv.lib already known stale. Result: 228 DCs → 21, pixel-identical render, verified. Applying the same trick to the 160 texture DCs is currently hung on a bug standalone testing could NOT reproduce (same library, same uglNewBMPEx+row-copy pattern, runs clean and byte-verifies) — so it's specific to qrender's own context, not the library or the row-copy logic, still open. Getting a trustworthy standalone repro cost five separate false negatives, all now documented: CRLF (BC silently mis-tokenizes LST-only line breaks instead of hard-erroring), $INCLUDE paths being relative to compiler CWD not source location, BC needing an explicit `, file.obj` destination or it silently produces a wrong stub, `/E` being a multi-module-project flag that produces a linked-but-inert EXE when misapplied to a standalone test, and the full library needing `/SEG:800` to link at all once uglview.asm pushed module count over LINK.EXE's default segment limit.

- 2026-08-24 — new `dos-mcb-memory-diagnosis.md` and `qrender-memory-map.md`: a 16 KB `memAlloc`/`REDIM` for the surface builder's colormap table hung the program with no error, while `memAvail&` reported ~260,000 bytes free. Root cause required abandoning BASIC's own memory introspection (`memAvail&`/`SETMEM`/`FRE`, which measure BASIC's far-heap *size*, not DOS's actual free memory) and walking DOS's MCB chain live in the dosbox-x debugger instead: DOS had exactly 9,312 bytes free system-wide, so the 16 KB request was arithmetically impossible to satisfy honestly — mgl's `bas_malloc` retry path (shrink BASIC's heap via `B$SETM`, retry `int 21h/48h`) handed back a block that didn't correspond to real headroom on an arena this fragmented, and a bare `REDIM`'s zero-init then corrupted whatever was actually there. Documented the walking method (4096-byte-per-read cap, `align:16` required or false positives are overwhelming, identify blocks by content not size since two disjoint origins — explicit `memAlloc()` calls carry mgl's own header, BASIC's automatic heap growth doesn't) and the full current memory map for dm3ish: DOS-side (9,312 B free total, `lm_base`/`lm_info`/font-atlas/texture-DC-structs identified by content, not guessed) and BASIC's-own-far-heap-side (249,005 B computed array-by-array vs. 248,672 B measured, 0.13% residual = allocator overhead). Fix identified: move `lm_base` (71,328 B) + `lm_info` (36,704 B) to XMS, reclaiming 108 KB; UMB is already linked and already fully consumed, not an available lever.
